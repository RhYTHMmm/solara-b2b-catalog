# Daily Work Log

## Overview

使用此技能生成项目当日工作日志，输出语言始终为中文，格式优先使用 Markdown。日志要基于事实，不要把未确认的推测写成已完成事项。

## Workflow

1. 确认日期：默认使用当前本地日期；如果用户指定日期，使用用户指定日期。文件名默认使用 `doc/WORK_LOG_YYYY-MM-DD.md`。
2. 收集素材：优先使用用户给出的要点、当前对话、已有工作日志、`git status`、`git diff --stat`、近期变更文件、测试或构建结果。
3. 归纳模块：从变更文件、功能边界或用户描述中提炼“可能涉及的模块”。模块名要具体，例如“首页数据获取”“Sanity 数据查询”“产品图片渲染”“组件拆分”，不要只写“前端”。
4. 区分事实和计划：已完成的工作写入“工作日志”；阻塞、疑问、缺陷和决策不确定性写入“遇到的问题”；尚未完成或建议继续推进的事项写入“下一步计划”。
5. 输出或更新文件：用户要求写入项目时，创建或更新对应 Markdown 文件；用户只要求生成内容时，直接在回复中给出完整日志。

## Log Structure

使用以下结构，按实际信息删减空段落，但保留“工作日志”“遇到的问题”“下一步计划”“可能涉及的模块”四个核心部分。

```markdown
# YYYY-MM-DD 工作日志

## 今日目标

用 1-3 句话概括今天工作的主线和目标。

## 工作日志

### 1. 模块或任务标题

- 记录具体完成事项。
- 写清楚关键文件、功能点、数据流或行为变化。

### 2. 模块或任务标题

- 继续记录其他完成事项。

## 遇到的问题

1. 问题描述：影响范围、当前判断、已尝试的处理方式。
2. 如果只是待确认事项，明确写成“待确认”。

## 下一步计划

1. 下一步要做的具体动作。
2. 需要验证、联调、补测试或补文档的事项。

## 可能涉及的模块

- 模块 A：关联的工作或风险。
- 模块 B：关联的工作或风险。
```

## Writing Rules

- 使用简洁、客观的中文表达，避免宣传口吻。
- 使用过去式描述已完成事项，使用“计划”“需要”“待确认”描述未来事项。
- 不编造测试结果、提交记录、接口返回或用户决策；没有证据时写“未验证”或“待确认”。
- 如果用户提供的是零散要点，先合并同类项，再补足上下文。
- 如果发现前一天日志中已有“下一步计划”，优先检查这些事项是否在今天完成，并在今天日志中闭环。
- 如果要更新已有日志，保留用户已有内容风格，只补充缺失信息和修正结构。

## Evidence Hints

生成日志时可参考这些本地信息：

- `doc/WORK_LOG_*.md`：历史日志格式和未完成计划。
- `git status --short`：当天可能变更的文件。
- `git diff --stat`：变更范围概览。
- `git diff -- <path>`：具体实现细节。
- `package.json`、测试输出、构建输出：验证和项目上下文。
