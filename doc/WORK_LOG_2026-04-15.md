### 4. 本地代理环境下的 Sanity 请求兼容处理

- 确认当前终端 Node 进程已拿到代理环境变量：
  - `HTTP_PROXY=http://127.0.0.1:7897`
  - `HTTPS_PROXY=http://127.0.0.1:7897`
- 排查发现：
  - 浏览器可以访问 Sanity Query URL
  - `curl -x http://127.0.0.1:7897 ...` 也可以快速打通 Sanity
  - 但 Node 侧请求链路不稳定，先后出现过 `UND_ERR_CONNECT_TIMEOUT`、`fetch failed`、`The operation was aborted due to timeout`
- 将首页 Sanity 请求改为显式使用 `undici` 的 `ProxyAgent`，不再只依赖 Node 隐式代理行为。
- 将请求方式从长 URL 的 `GET` 调整为 `POST /data/query/{dataset}`，并改用 `apicdn.sanity.io` endpoint，以降低长 GROQ 查询通过代理时的不稳定性。
- 在 `package.json` 中增加 `undici` 依赖，在 `README.md` 中补充这一请求链路说明。

## 遇到的问题

1. 首页空白页

   页面看起来是空白，但根因不是 CSS，而是 SSR 在等待 Sanity 数据时卡住，浏览器没有及时拿到完整 HTML。

2. 浏览器、curl 与 Node 的代理行为不一致

   浏览器可以访问 Sanity，`curl` 通过代理也可以正常访问，但 Node 的请求在同一代理环境下仍会出现连接失败或超时。

3. 长查询在代理链路中的稳定性问题

   首页 GROQ 查询较长，直接通过 GET URL 传输时，在本地代理环境下更容易出现超时或请求链路不稳定。

4. 当前环境验证结果与本地结果不完全一致

   当前自动化执行环境中访问 `127.0.0.1:7897` 会报 `EPERM`，这属于沙箱限制，不等同于用户本机代理不可用。
